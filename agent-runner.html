Guardrails for unattended AI work

Long agent jobs with the bill checked first

A small command-line runner that sends a written brief to Claude through the Claude Agent SDK, with explicit auth, budget and turn guards, and loops fresh passes until the brief's done file appears.

2billing paths, an API key or a subscription login; the run aborts before any work if the session reports the wrong one
$20default budget per pass, passed to the SDK's built-in dollar budget
0retries: the loop stops on the first capped or failed pass and says why

The problem

Long agent jobs (build a guide, refactor a folder, work through a checklist) are easier to hand off as a written brief than as a live chat. Running them unattended raises three practical questions: which account pays, how to stop a run that goes over budget, and how to continue a job that does not finish in one pass.

The first is easy to get wrong. A run authenticated with an API key bills that key's account; a run on the subscription login draws on the subscription instead. If an API key happens to be set, it silently wins over the login.

What I directed

I specified the options, the guards and their acceptance tests, and verified the results before using it on real work. An AI coding agent wrote the code from my written brief.

  • Who pays is checked, not assumed. The billing path is a flag, and the runner aborts before the first tool call if the key source the session itself reports does not match.
  • Use the built-in budget rather than counting cost by hand. The SDK reports cost only in its final result message, so a hand-rolled running total could not stop a run in time.
  • Fresh passes over one long session. Context grows with every tool result; a new pass that reads short progress notes is cheaper than dragging a full transcript along.
  • Stop on the first failure. A pass that crashed or hit a cap usually needs a person to look before more money is spent, so the loop does not retry.
  • Written rules still apply. The runner loads user and project settings, so the operator's standing rules apply to unattended runs too.
  • Spend nothing on a bad command. The loop validates its arguments before spending anything.

How the results were verified

  • The exact key-source string was found by a live test with the smallest model rather than guessed.
  • The auth guard, settings loading, and a fresh run plus a resume were tested with the smallest model before the first real brief.

The outcome

Working, and used for real multi-pass jobs in October 2026. The subscription login became the loop's default on 2026-10-25.

Each pass leaves a readable log and a raw one. A crash still prints the session id, so a follow-up can pick up in the same session.

Honest limits

  • No automated tests.
  • Stopping a pass by hand part-way can leave the working folder mid-edit.
  • The loop script needs zsh.
  • By default the agent runs tools without asking, so the runner should be pointed at a folder it is allowed to change, or given a stricter mode.

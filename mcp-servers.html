Tools shaped for the model that reads them

Giving a local model tools it can use

Six small MCP (Model Context Protocol) servers that give a locally hosted language model what it lacks: live world events, market prices and company fundamentals, a dependency vulnerability audit, a read-only study coach and equation OCR (reading equations from images).

The problem

A local model knows nothing after its training cutoff and cannot look anything up. Public data services do publish their own MCP servers or APIs, but they are built for large cloud models: one hosted server lists 90 tools and about 100k tokens of schema, which at a local model's speeds costs minutes per new chat and most of the context window.

Others need an interactive login that a simple bridge cannot refresh. So each server here is a thin, hand-shaped wrapper that a mid-sized local model can pick from and read without drowning in the answer.

What I directed

I set the goals and constraints (a local model's token budget, read-only, no trading tools), wrote the acceptance checks, and verified the results against the live services and my local model stack. The agents wrote most of the code to that specification.

  • Shape tools for the model that will read them. The audience is a local model in the tens of billions of parameters, not a frontier cloud model. Each tool list is short, each description says when to use the tool, defaults are small, and tools that can only fail on the free plan are left out entirely, because a dead tool is noise the model has to read past.
  • Do arithmetic in code, not in the model. The comparison tool returns ranked percent changes rather than raw bars. Arithmetic over long number series is where small models go wrong, and a wrong number reads as a real one.
  • Make empty data loud. A bad ticker does not raise an error upstream; it comes back as empty values. The server checks for that and returns an explicit error, because a model handed nulls tends to report them as data.
  • Measure before raising a cap. The history tool was hitting the reply cap, so the format changed instead of the cap.
  • Read-only by design. There are no trading or order tools anywhere, and the study-coach server leaves out every route that would fetch or answer a question.
  • Errors a model can read. Errors come back as plain-English strings the model can relay, never as stack traces, and missing credentials return a setup message instead of failing or hanging.

How the results were verified

  • Company data server: working. Verified with live data on 2026-09-18, mounted in a local chat front end and in real use.
  • Vulnerability audit: working. Checked on 2026-11-13 through an in-memory client, covering findings, a missing path and a missing scanner.
  • Study coach: working against the sample bank. Checked on 2026-11-13 against the practice app serving its 21-item sample bank; all six tools returned data.
  • World events server: built. 15 tools listed, the no-login and expired-login paths return the setup message, and a quota-free self-test ran against the live endpoint.

The outcome

Six servers, each one Python file that runs with one command. The study coach reads from another project here, the practice app built around the mistake.

The README gives each server's status separately, from "working" to "built, not yet run with a key".

Honest limits

  • World events: no account login had been done, so reply sizes on real data are unverified.
  • Market prices: built, not yet run with a key. The free-plan behavior was probed with keyless requests only.
  • Equation OCR: used in the original stack and not re-run for the public copy; only the tool listing and the bad-image error path were re-checked.
  • No automated test suite is included, and the study coach's replies on a long practice history are unmeasured.
  • The third-party limits in the README carry the date they were checked. Plans change.
